# 調査ノート：TableCheck API で取得できる予約・顧客データ（再調査）

> 出典：本セッションの3エージェント並行調査（CRM/顧客・予約読み取り・パートナーアクセス）。2026-06-12。
> **重要な限界**：TableCheckの一次ドキュメント（`api.tablecheck.com/*/docs` のOpenAPI、`tablecheck.atlassian.net` のConfluence）は**全て403**でこの環境からは直接取得不可。以下は検索エンジンが引用したドキュメント本文＋第三者連携ページ＋実在のGitHubクライアントに基づく。**フィールド名レベルの確定は要・ポータルアクセス**。

## 結論（ユーザー見解の検証）
**「TableCheck APIでアレルギー等の細かい顧客情報が取れる」は ほぼ正しい。** 以前の「API非対応」は Booking API の**“予約作成”能力**の話で、**“読み取り＋CRM”は別**だった。アレルギー・好み・人数・時刻・席・予約変更は取得できる。**唯一の例外＝構造化された「コース事前選択」**で、これは memo（自由文）でしか来ない。

## 取得可否マトリクス
| 項目 | API取得 | 形式 | 確度 |
|---|---|---|---|
| 来店時刻（start_at） | ✓ | 構造化 | 高 |
| 人数（pax） | ✓ | 構造化 | 高 |
| 席/テーブル・ステータス | ✓ | 構造化 | 高 |

## 連携の仕組み（確定）
- **Sync v1 = 薄いWebhook**：`SyncEvent`（type＋IDのみ、データ本体は含まない）→ イベント受信後に **CRM v1 / Booking v1 / POS v1 から本体をフェッチ**（pull）。ポーリングも可（≤1回/30s、窓≤24h、≤1000件）。
- **アクセス＝審査制**：`api@tablecheck.com` に用途記述＋連携図を提出→ポータル承認→Sandbox/Live鍵。**コンポーネント別に個別申請**（CRM/Sync/Booking/POS…）。Booking APIは「special arrangement」、POS APIは「POSベンダー向け」。**法人格が事実上前提**。

## 決定的な実例（実在の証明＋競合シグナル）
**Annoncer**（キッチンディスプレイ/管理システム）が、TableCheck連携で **「アレルギー・好み・ペーシング・人数をリアルタイムで厨房へ」「皿・席ごとにアレルゲンと特別リクエストを自動表示、再入力不要」** を**本番で実現済み**。
→ ①「厨房向け第三者がTableCheckからアレルギーを取れる」ことの実証。②**同種の競合が既に存在**（PrepFlowは仕込み逆算で差別化、Annoncerは提供時のKDS寄り）。

## 唯一の未確定事実
`GET /crm/v1/customers/{id}` の正確なスキーマ（アレルギーが `allergies` 等の構造化配列か、自由文か）。エビデンスは**自由文＋タグ寄り**。確定にはポータル承認後にスキーマ取得、または `api@tablecheck.com` へ直接照会：
> 「CRM v1 customer は allergies/dietary を構造化（enum/配列）で返すか、自由文か。Syncイベントに含まれるか。」

## 要件への影響（v1.1で反映）
1. **FR-13 を拡張**：TableCheckを「人数・時刻のみ」から「人数・時刻・席・ステータス・**顧客プロフィール（アレルギー・好み・タグ）・予約変更イベント**を構造化/半構造で取得、**コースのみ memo→テンプレ・マッピング**」へ。Sync→pull機構・審査制を明記。
2. **「Directだけが構造化の唯一ソース」を訂正**：アレルギー・顧客情報はTableCheck APIでも取得可。Directの独自価値は **構造化コース選択＋送客手数料ゼロ＋自社ブランド導線** に絞られる（依然有効）。
3. **席番アレルゲン（FR-26/47）の供給源にTableCheck CRMを追加**（Direct/手入力と並ぶ）。
4. **§15ベンチマークに Annoncer 追加**（TableCheck連携の厨房システム＝実証＆競合）。
5. **パートナー申請を早期開始**（審査リードタイム＋法人化前提のため、P3だが手続きは前倒し）。
6. **NFR-06 維持**：取得源がどこであれアレルギーは“参考”、最終確認は人。

## 追補（v2・2026-06-12）— ユーザー提供のAPIポータル目次で「コースも構造化」と判明
**以前の「コースはmemoのみ」は誤り（API surfaceの取り違え）。** ポータル目次（ユーザー提供・一次情報）＋裏取り検索で確定：

- **CRM API v1（深い同期用）** は別物で、**予約（Reservations）を構造化で読み書き**できる：
  「既存予約の更新（**日時・人数・コース・席タイプ**の変更）」「全予約取得（一覧・個別）」「新規予約作成」「予約フラグ」。`PUT /reservations/{id}`（時間/人数変更は Blockage 先行）を検索で確認。
  → **コース・席タイプは構造化フィールド**（読み書き可）。
- **顧客（Customers）**：「**おもてなし情報（アレルギー・好み・スタッフメモ）の同期**」「会員/VIP（Memberships）」。→ アレルギーは一級の同期対象。
- 以前ヒットした「menu item booking is not supported / memo」は **Booking API（外部ウィジェット/アグリゲーター向け）** の制約で、**CRM API には当てはまらない**。

**結論の更新：完全な双方向連携が可能。**「コースmemo→手動マッピング」の前提は**撤回**（TableCheck店ではコースも自動取得）。確認が残るのは「おもてなし＝アレルギーが enum か自由文か」の粒度のみ（ポータルでスキーマ取得 or api@tablecheck.com 照会）。

### さらにできること（提案・未承認＝v1.2候補）
- **書き戻しの閉ループ（新機軸）**：キッチンの 86/売り切れ・追い仕込み限界 → **Availability/予約枠へ書き戻し**（POS/Booking API）。予約→仕込み（下り）だけでなく**仕込み→予約（上り）**を閉じる＝Annoncerにも無い。※「台帳化はしない」線は維持し、**書き込みはキッチン由来シグナル（86/空席）に限定**。
- **おもてなし構造化の活用**：好み・記念日 → 特別仕込みタスク自動生成。会員/VIPランク → VIP卓の特別対応フラグ。
- **Messaging API**：来店前の**アレルギー事前確認メッセージ**（厨房リスク低減）。
- 戦略：第一ターゲットがTableCheck層で、かつ**TableCheck自体が送客手数料ゼロ（席数連動の月額）**のため、Directの「手数料ゼロ」優位は対 食べログ/ぐるなび限定。→ **TableCheck深掘り連携を Direct(P3.5) より前倒しする価値**。
