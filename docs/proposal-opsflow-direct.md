# 実装提案：業務フロー管理（Ops Flow）＋ 予約ハブ ＋ PrepFlow Direct（直販予約ページ）

> ステータス：**提案（v0.4候補）**。承認後に `requirements.md` へ反映する。
> 前提：requirements v0.3（FR-01〜30・イベント駆動§14・3テーマ§13）の上に積む。一人開発・運営。

---

## 0. 結論（設計原則3つ）

1. **予約は「ハブ」であって「台帳」ではない。**
   PrepFlowは予約の*正規化された読み取り*（人数・時刻・コース・アレルギー）だけを行い、台帳業務（席割り・オーバーブッキング管理・顧客CRM）は**あえて持たない**。台帳はお店の現状のまま（TableCheck/トレタ/ぐるなび/紙）。→「今のやり方を変えずに導入できる」が営業上の最強の売り文句であり、ユーザーの懸念（台帳一体型は売りにくい）への直接回答。

2. **業務フロー（カミナシ/V-Manage領域）は“新モジュール”ではなく“同じT−軸の別レーン”。**
   開店前チェック・清掃・発注・クローズ作業を、既存の仕込みタスクと同じ逆算タイムライン／3ビュー／アラート機構に**混在**させる。実装の大半は既存機構（FR-16チェックシート・FR-17定期タスク・FR-22アラート）の再利用で済み、UIも増えない。

3. **PrepFlow Direct（CHILLNN型直販ページ）は“もう一つの予約ソース”として後付けする任意アドオン。**
   §14のイベント駆動アーキテクチャ上、Directは「イベント発行者の一つ」にすぎない。**そしてDirectだけが、APIでは取れない構造化データ（コース事前選択・席ごとアレルギー）を完全な形で仕込みエンジンに流せる唯一のチャネルになる**——予約API問題（TableCheck Booking APIは構造化コース非対応）の自己解決策。

## 2. モジュールA：業務フロー管理（Ops Flow）

### 機能要件（追加 FR-31〜33）
| ID | 機能 | 概要 | Ph |
|---|---|---|---|
| FR-31 | 業務フローテンプレ（デイレール） | 開店前・営業中・閉店後のルーチンタスクを **T−/T+ アンカー**（例：清掃 T−1:00、レジ締め T+0:30）または時刻・曜日で定義。役割（ホール/厨房/店長）を付与 | P1.5 |
| FR-32 | 統合表示 | 業務タスクが仕込みタスクと**同じ3ビュー・同じ逆算レール**に混在。区別は左端アイコン（🍳仕込み/🧹業務）と数量チップの有無のみ。色は増やさない | P1.5 |
| FR-33 | クローズフロー | 閉店時に「クローズチェック → HACCP記録(FR-16) → 引き継ぎ(FR-23) → 日次サマリー」を1本の流れで完了。最後に「本日の営業を締める」＝1日のゲート（ライン点検の対） | P2 |

### カミナシ/V-Manageとの違い（守るべき一線）
- **やる**：単店の1日の運行表（時間アンカー・チェック・写真手順・未実施アラート）。
- **やらない**：本部→多店舗一斉配信、組織階層、汎用ワークフロー設計画面。←これをやるとV-Manageの土俵で戦うことになり、soloの保守も破綻する。
- 差別化は一貫して「**予約・T−軸に紐づく運行表**」（例：予約14名なら客席セットのタスク量が自動で変わる）。

### 実装規模
既存のRecurringRule＋チェック機構の拡張＋アイコン1種＋テンプレ画面に「業務」タブ追加。**目安2〜3週間**。リスク小。

## 3. モジュールB：予約ハブ（FR-34）

```
Reservation {
  id, service_day_id, source(manual|csv|email|api|direct),
  status(confirmed|request|cancelled), party_size, arrival_time,
  course_id?, per_guest_notes[]?(アレルギー参考・自由文),
  external_ref?(台帳側ID), created_via
}
```
- **やる**：正規化・ソース横断の合算（コース別人数）・重複疑いの警告・変更差分の仕込みへの反映（「2名増えました→煮切り+28ml」のトースト）。
- **やらない**：席割り・空席管理・顧客DB・ノーショー課金（Direct以外）。
- 既存の「本日のサービス設定」画面はこのハブのUIにそのまま昇格（取込済み予約リスト＝実装済みワイヤー）。

## 4. モジュールC：PrepFlow Direct（CHILLNN型・直販予約ページ）

### コンセプト
CHILLNNが宿でやったこと（手数料の高いOTA依存 → 世界観のあるリッチな直販ページ＋低コスト決済）を、飲食の文脈に翻訳する：
- 食べログ/ぐるなびの**送客手数料（夜 ¥200/人前後）への不満**は調査で確認済み。月200人なら**月4万円超**。
- 高級店はすでに「コース事前決済・前払いおまかせ」文化（OMAKASE/Pocket Concierge/TableCheck Pay）。**事前決済つき直販**は市場慣行に合う。
- **Instagram/Googleビジネス → 自店の美しい予約ページ**という導線を、月額固定・送客費ゼロで提供。

### 予約フロー（店のページ上）
```
日時スロット選択 → 人数 → コース事前選択（必須）
→ 席ごとのアレルギー・苦手食材アンケート（参考情報として取得）
→ 事前決済 or デポジット（Stripe・ノーショー対策）→ 確定/リクエスト
```
→ この瞬間、**構造化されたコース×人数×アレルギーが予約ハブへ直行**し、仕込みが完全自動算出される。**APIでは不可能だった“完全自動の逆算”がDirect経由予約でのみ成立**＝直販比率を上げるほど店が楽になる、という内製ループ。

### 在庫の割り切り（台帳と衝突しない仕組み）
- 業界慣行どおり**チャネル別アロットメント**：店は「直販枠＝1日◯席（スロット別）」だけ設定。満枠で自動クローズ。
- 台帳との双方向同期は**しない**（Direct-3まで保留）。直販枠は店が台帳に手で転記（=今、一休や食べログの枠でやっていることと同じ運用）。
- これにより「TableCheckをやめてください」と言わずに売れる。

### 段階導入（solo工数を守る）
| 段階 | 内容 | 規模感 |
|---|---|---|
| **Direct-1** | リクエスト型予約＋事前決済（Stripe Checkout）。ページはテンプレ1種（写真・コース・ポリシー）。店が承認→確定メール | 1.5〜2ヶ月 |
| **Direct-2** | アロットメント在庫で**自動確定**・キャンセルポリシー自動執行・リマインドメール | +1〜2ヶ月 |
| **Direct-3** | 台帳API連携（TableCheckパートナー等）で直販枠を台帳へ自動反映 | 法人化後・P4併走 |

### 収益モデル（追加レバー）
| 項目 | 案 |
|---|---|
| Directアドオン | **+¥9,800/月**（Standard以上に追加）。送客手数料**ゼロ**を明示 |
| 決済 | Stripe実費（3.6%）＋**0〜0.4%**の薄いマージン（将来の収益レバー。当初はゼロでも可） |
| 比較訴求 | 食べログ純予約 月200人 ≒ **¥44,000** vs Direct **¥9,800定額** |
| 副次効果 | 予約ページ下部の「Powered by PrepFlow」＝**獲得チャネル**（CHILLNN型のバイラル） |

### 新FR（FR-35/36）
| ID | 機能 | Ph |
|---|---|---|
| FR-35 | Direct予約ページ（リッチページ・スロット・コース事前選択・アレルギーアンケート・事前決済/デポジット・確定/リクエスト） | P3.5 |

## 5. ロードマップ更新案

| Ph | 内容 | 備考 |
|---|---|---|
| P0–P1 | 変更なし（仕込みコア） | — |
| **P1.5** | **Ops Flow（FR-31/32）** | 2〜3週間。Lite/Standardの価値を底上げ |
| P2 | 営業中モード等（既存）＋ FR-33クローズフロー | — |
| P3 | 公式API・多言語・リプレイ（既存） | — |
| **P3.5** | **PrepFlow Direct-1→2（FR-35/36）** | 法人化・Stripe審査後。Directアドオン課金開始 |
| P4 | Service Sync（既存） | Direct-3（台帳同期）を併走 |

**順序の理由**：Ops Flowは安くて速く既存顧客の解約率を下げる。Directは収益・差別化インパクトが最大だが、決済・キャンセル対応などsolo負荷が高いので、課金基盤と顧客ベースができた後（P3.5）に置く。

## 6. リスクと割り切り

| # | リスク | 対処 |
|---|---|---|
| D-1 | Directが「予約システム開発」の沼（空席管理・当日変更・サポート）に化ける | リクエスト型から開始（Direct-1）。台帳機能は永久にやらないと明文化 |
| D-2 | TableCheck等とのチャネルコンフリクト | 「台帳はそのまま・直販枠だけ」ポジションを営業資料で固定。将来はパートナー化（P3公式API）も視野 |
| D-3 | 決済・キャンセル紛争のsolo負荷 | キャンセルポリシーをテンプレ強制・Stripe紛争フローに委譲・返金は店判断のセルフサーブ |
| D-4 | 法務（特商法表記・資金移動） | Stripe Connect（店舗直収）で資金を預からない設計。特商法・規約テンプレ同梱 |
| D-5 | Ops Flowの機能肥大（V-Manage化） | 「単店・T−軸アンカー」以外の要望（本部配信等）は断る基準を要件に明記 |
