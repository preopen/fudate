## 1. 背景・目的

### 1.1 背景（調査サマリ）
- **需要は強い**：人手不足（正社員不足56.5%/非正社員不足74.8%）、外食倒産過去最多（2024年894件）、外食の食品ロス66万トン（過剰仕込みが一因）、薄利（純利益率3〜5%）。脱・属人化／標準化は業界の認識された課題。
- **白地**：「料理→構成要素→サブ仕込みの階層×全完了で自動ロールアップ」×「予約から逆算した仕込みタイムライン」を統合した製品は不在。
- **市場**：高級店オンリーは小さいため、客単価¥5,000–10,000帯（コース・予約・仕込みが効く店、推計3〜5万店）まで拡大して狙う。
- **競合の現実（V-Manage）**：チェーン本部→店舗の店舗オペ管理「V-Manage」が¥5,000/店舗/月で普及（時系列タスク＋マニュアル動画＋チェック＋ダッシュボード＋HACCP）。ただし仕込み“量”の算出・予約逆算・成果物の階層ロールアップは非対応。→ PrepFlowは「予約連動の数量・段取りインテリジェンス」で差別化し、UIの“やることリスト＋メディア手順”はV-Manageの実証済みパターンを採り入れる。
- **制約**：予約APIはゲート式で個人に不利／TableCheck予約APIは構造化コース非対応／飲食SMBは低WTP・高解約／営業中の障害は即事故。→ 個人運営でも生き残れる設計が大前提。

### 1.2 目的（JTBD）
> **「今夜の予約◯名分、誰が・何を・どの順で仕込めば開店に間に合うか」を毎日5分で確定し、抜け漏れ・過剰仕込み・属人化をなくす。**

### 1.3 成功の定義
- パイロット店で週5日以上の継続利用 ≥70%、月次解約率 <5%。
- 一人運営で ~100〜300店 × ¥6,000〜20,000/月 = 月商¥100万〜数百万 の持続事業。

## 2. スコープ

### 2.1 対象（In）
コース／予約主体・厨房1〜5名・ネット予約利用済み、客単価¥5,000–10,000の業態（鮨・ビストロ・モダンフレンチ/イタリアン・創作和食・高単価居酒屋）。日本（多言語は将来）。

### 2.2 対象外（Out / 当面）
チェーン本部の多店舗統制（本部一斉配信等）、**発注・仕入・在庫・原価計算・会計（＝連携も含めて永久に作らない。必要な店は Smart Rabbit / BtoBプラットフォーム等の専用ツールを併用）**、POS/KDSリアルタイム連携（P4 Service Syncを除く）、アレルゲンの“正”管理、複雑な権限/監査、モバイルネイティブアプリ。
材料BOM（メニュー→材料の分量登録＝レシピ分解）も**作らない**：仕込み数量は「1人前の出来上がり量」＋自己補正（FR-09）で扱う。

### 2.3 アクター
| アクター | 役割 |
|---|---|
| オーナーシェフ（管理者） | テンプレ作成、当日設定、課金管理 |
| 厨房スタッフ（一般） | 当日ボードで仕込みチェック |
| （システム） | 数量算出・逆算・ロールアップ・アラート・学習提案 |
| （将来）予約システム | 来店時刻・人数の供給元（v1.5メール／v2 API） |

## 3. 用語定義
| 用語 | 定義 |
|---|---|
| 料理(Dish) | コースを構成する1皿 |
| 構成要素(Component) | 1皿のパーツ（例：鯛の下処理、柑橘オイル） |

| ロールアップ | 子の全完了で親が自動完了する仕組み |
| 逆算タイムライン | 開店時刻から所要時間を引いて着手時刻を算出 |
| 定期タスク | 毎営業日/曜日指定で自動生成される仕込み |
| 電子チェックシート | 衛生管理/HACCP記録（紙の置換） |

### 4.2 営業全般・予約起点の拡張（v0.4 追加 — `proposal-opsflow-direct.md` 承認済み）
設計原則：**予約は「ハブ」であって「台帳」ではない**（席割り・空席管理・顧客CRMは持たない）。業務フローは**同じT−軸の別レーン**として既存機構（FR-16/17/22）を再利用する。

| FR-32 | 統合表示 | 業務タスクを仕込みタスクと**同じ3ビュー・同じ逆算レール**に混在表示。区別はアイコンと数量チップの有無のみ（色は増やさない）。**Liteに含める** | S | P1.5 |

| FR-34 | 予約ハブ | Reservation正規化（人数・来店時刻・コース・アレルギー参考・出所）。ソース5種（手入力/CSV/メール/公式API/Direct）の合算・重複疑い警告・変更差分の仕込み反映。**差分時、対象タスクが完了済みなら「追い仕込み」タスクを自動生成**（FR-19と同機構の営業前版）。UIは「本日のサービス設定」画面を昇格・統合（二重開発を避ける）。**台帳業務はやらない** | S | P2 |
| FR-35 | PrepFlow Direct 予約ページ | CHILLNN型のリッチな直販予約ページ：スロット→人数→**コース事前選択（必須）**→席ごとアレルギーアンケート（参考）→**事前決済/デポジット（店舗ごとに必須/任意/なしを設定可）**→確定/リクエスト。Stripe Connect（店舗直収・資金を預からない） | C | P3.5 |

### 4.3 軽量レシピ層（v0.5 追加 — `note-smartrabbit.md` 反映）
方針：**フルのレシピ管理（材料BOM・原価・栄養）は作らない。** 仕込み数量に必要な最小限＝「出力量の当て方」だけを持ち、Smart Rabbit「単位売上」型の自己補正（FR-09）でレシピを“育てる”。**材料登録・発注・在庫・原価は対象外（§2.2）。**

| ID | 機能 | 要件概要 | 優先 | Ph |
|---|---|---|---|---|
| FR-37 | スケール則＋自動/手動フラグ | 仕込みアイテムごとに出力の決め方を選択：`per_cover`（人数×係数）／`per_portion`（1人前×人数, 例 14貫）／`fixed_batch`（固定バッチ, 例 出汁5L・端数切上げ）。基本は自動算出、イレギュラーは手動上書き。係数・歩留りは普段非表示、ワンタップで展開 | S | P1 |
| FR-38 | サブレシピ参照（共有半製品の合算） | 煮切り・出汁等の半製品を再利用アイテムとして定義し、複数の料理が参照。当日は**重複を1タスクに集約**し合計量を算出（「煮切り 合計◯ml／全コース」）。**任意**（使わなければ料理直下のタスクとして動作） | C | P1.5 |
| FR-39 | シミュレーション並走（導入時） | 本番適用前に、実際の仕込み量と PrepFlow推奨量を一定期間並走比較し差分を提示（Smart Rabbitの導入手法を移植）。**2モード：①遡及（過去の予約・仕込み記録がある店）／②前向き並走（記録がない店は導入後2週間、普段どおり仕込みつつ記録）**。パイロットの信頼獲得・係数初期化に使う | S | P0 |

> 補足：PrepFlowはSmart Rabbitと違い**予約という確定情報起点**なので、売上統計推定より正確・先行。両者は「発注 vs 仕込み生産」で**補完関係**だが、本プロダクトでは発注側は持たず**併用を案内するに留める**（連携も作らない）。

### 4.4 運営現実への対応（v0.6 追加 — 実装案の検証で抽出）
高級店・コース店の実際の運用（前日仕込み・二部制・共有端末・繰越）に合わせる。**T−軸の一般化**が中核で、既存ロジックの拡張で実装する。

| ID | 機能 | 要件概要 | 優先 | Ph |
|---|---|---|---|---|
| FR-40 | 複数日リードの仕込み | リードが営業日を跨ぐタスク（昆布締め一晩・漬け2日・熟成等）は **N日前のボードに出す**。基準は**その営業日の予約数**（未来日の予約を使用、無ければ予測/手入力で補完）。逆算は**営業日カレンダーで定休日をスキップ**。当日ボードは「今日やる＝今日提供＋数日先の前倒し分」を1枚に統合（種別タグで区別） | **M** | P1 |
| FR-41 | 二部制・複数営業帯 | ServiceDay＝**日付 × 営業帯**（昼/夜、第一部/第二部など）。各帯に T=0（開始時刻）。カウントダウン・逆算・残数は**次に来る帯**を基準。帯ごとにコース別人数を保持 | **M** | P1 |
| FR-42 | 繰越残量の差引 | 営業後の残量（例「煮切り100ml残」）をクローズ時に記録（FR-23引き継ぎを構造化）し、**翌営業日の推奨量から自動で差引**。**在庫管理はしない**＝当日推奨の補正のみ（賞味期限内の半製品が対象） | S | P2 |
| FR-43 | 完了者の記録（共有端末） | タブレットは共有のため、完了タップ時に**担当チップを選ぶ（任意）**＝誰が締めたかを記録。HACCP記録者（FR-16）・引き継ぎ（FR-23）にも流用。ログインは強制しない | S | P1 |
| FR-44 | 紙の仕込みリスト印刷 | PASS SHEETテーマを**A4で印刷／PDF**。紙運用文化・停電/端末故障時のバックアップ（NFR-01の物理的フォールバック） | C | P2.5 |

**設定追加：営業日カレンダー（定休日・祝日）** — 定休日・臨時休業・祝日を登録。**FR-17（定期タスク生成）とFR-40（複数日逆算のスキップ）の基礎**。設定の「営業・T−規律」に追加。

### 4.5 モード制（任意機能の切り分け / v0.8）
PrepFlowの任意機能は**「モード」**として束ね、設定で**ON/OFF（既定OFF）**する。店は必要なものだけ有効化でき、OFFの店は従来運用で全コア機能が使える（必須化しない）。現在のモード：**ラベルモード（§4.5）／HACCPモード（§4.6）**。両モードは独立だが、**冷蔵庫QRレンズ（FR-49）で合流**する（有効な方の情報だけ表示）。

## 6. データ要件（論理モデル）
```
Restaurant ─┬─ Section ─── Staff
            ├─ CourseTemplate ── Dish ── Component ── PrepTask
            │                                 (output_unit, scale_mode[per_cover|per_portion|fixed_batch],
            │                                  qty_coeff, yield_pct, auto|manual,        ※FR-37
            │                                  shelf_life_days,                          ※FR-20/45 賞味
            │                                  duration_min, lead_min_before_open, section)
            │                                   └─ MediaAsset (type: manual/photo/video)
            │                                   └─ RecurringRule (毎営業日/曜日指定)
            │                                   └─ uses[] → PrepTask(サブレシピ参照, 任意)  ※FR-38
            │                                   └─ I18nText (多言語ラベル)   ※FR-18
            ├─ ServiceDay (date, **service_period**[昼/夜/一部/二部], open_time(=T0),
            │              covers[コース別], note)                       ※FR-41
            │     ├─ TaskInstance (status, assignee, **completed_by**?, checked_at,
            │     │                **prep_day**(=提供日−リード日数, 営業日カレンダー考慮)) ※FR-40/43
            │     │     └─ Alert (type: 未実施/遅延)
            │     └─ WasteLog (planned_qty, made_qty, leftover_qty,
            │                  **carryover_to_next**?)                  ※FR-09補正入力 / FR-42繰越
            ├─ BusinessCalendar (closed_days[], holidays[], temp_closed[])  ※設定追加・FR-17/40の基礎
            ├─ ChecklistTemplate ── ChecklistItem
            │          └─ ChecklistRecord (date, value, recorded_by)   ※FR-16 HACCP
            ├─ ★ラベルモード（任意・既定OFF）
            │     Label (task_instance_id, printed_at, made_qty, expire_at(=仕込日+shelf_life),
            │            qr_token, fifo_color?, status[active|remaining|used|wasted],
            │            remaining_qty?, storage_unit_id?)              ※FR-20/45/46
            │     Printer (model, conn[usb|bt|net], paper_size, is_default)  ※FR-48
            └─ ★HACCPモード / 保管（任意・既定OFF）
                  StorageUnit (name[冷蔵1/冷凍/ウォークイン], zone[refrigerated|frozen|chilled|ambient],
                               qr_token, temp_min, temp_max)            ※FR-49 冷蔵庫QR
                  TempLog (storage_unit_id?, kind[fridge|heating-CCP], value, logged_at, by)  ※FR-51
```
> Labelは「印刷物」かつ「QRで残量を返す入力口」。`status/remaining_qty` の更新がWasteLog/繰越(FR-42)へ環流。**Labelは半製品の現在地ビュー(FR-45)の実体**＝食材在庫テーブルではない。
> `PrepTask.default_storage_zone?`（任意）＝品目の既定ゾーン。`Label.storage_unit_id` は**ゾーン整合の参考**で、出し入れ追跡はしない（FR-49レンズ＝読み取り専用）。
> ※ **材料(Ingredient)テーブルは持たない**（材料BOM＝レシピ分解は対象外）。PrepTask が扱うのは「出来上がりの出力量」のみ。

主要ロジック：
1. 量＝scale_modeで決定：`per_cover`=人数×係数÷歩留り／`per_portion`=1人前×人数／`fixed_batch`=固定量を端数切上げ（FR-37）
2. 合算＝同一サブレシピ参照（uses[]）を1タスクに集約し合計（FR-38, 任意）
3. 着手＝`T0(営業帯開始) − (リード + 所要)`。リードが日を跨ぐ場合は **prep_day = 提供営業日 − リード（営業日カレンダーで定休日スキップ）** に前倒し（FR-40/41）
4. ロールアップ＝子全完了で親完了
5. 定期＝RecurringRule×営業日カレンダーからTaskInstance自動生成／アラート＝T0−n分で未実施を検知
6. **自己補正レシピ**＝WasteLogの`余り/製造`実績で `qty_coeff`(1人前量) を自動補正（FR-09）／導入時はシミュレーション並走で初期化（FR-39）
7. **繰越差引**＝前日 `carryover_to_next` を翌営業日の推奨量から減算（FR-42, 賞味期限内のみ）

## 13. UIテーマ（3テーマ採用）
配色は「黒文字＋白基調＋グレー」を共通骨格とし、**同一レイアウトでトークンのみ差し替える3テーマ**を設定で切替（店の文化に合わせる）。ビュー切替（今これ／皿ごと／担当）は3テーマ共通。

| テーマ | 思想 | 配色 | 対応案 |
|---|---|---|---|
| INK | 完全モノクロ。「いま」は黒地反転だけで示す | 色ゼロ | `redesign2-1-ink` |
| PASS SHEET | 3つ星厨房のパスシート（帳票）をそのまま画面に | 完全モノクロ | `redesign2-2-passsheet` |
| ONE ACCENT | 「色＝時間」の一点ルール。朱はカウントダウン/NOW/遅延のみ | 朱1色＋無彩色 | `redesign2-3-oneaccent` |

UI原則（3テーマ共通）：
- **緊急表現は色を増やさず**、反転・動き・音で階層化（FR-22）。
- **手が汚れている前提**：完了は大ターゲット＋長押し可、5秒アンドゥ、将来は音声完了。
- **ダークモード＝夜厨房**：INKをそのまま反転（白地→黒地）。
- T−逆算・開店カウントダウン・ライン点検ゲートを全テーマで常時表示。
- **設定の保存モデル**：即時保存＋トースト「保存しました・元に戻す」。確認ダイアログは破壊的変更（削除・モードOFF等）のみ。

## 14. アーキテクチャ方針（イベント駆動）
将来のPOS連携（P4）の費用と結合度を下げるため、**最初からイベント駆動**で設計する。主要ドメインイベント：

```
task.completed / subtask.completed / dish.rolledup / phase.changed
service.started(T=0) / course.fired / course.held / item.served
par.updated / par.depleted(→追い仕込み自動生成) / label.printed
alert.raised(level: toast|banner|fullscreen)
reservation.created / updated / cancelled (source: manual|csv|email|api|direct)
direct.booking.requested / confirmed / deposit.paid
label.printed / label.scanned(status: remaining|used|wasted) / item.expiring  ※FR-20/45/46
storage.scanned(unit_id) / inspection.done / temp.logged(kind: fridge|heating)  ※FR-49/50/51
```

- キッチン側は購読者、ホール/ハンディ/自社POSは**イベント発行者として後から挿す**。
- これにより P0〜P3 を単体で完成させつつ、P4で**POSを“発行者”として接続するだけ**にできる（連携費用の最小化）。
